## 二、逐项需求分析

### 优化项 ①：裁判模型（LLM-as-judge）执行落地

**要解决的问题**：开放题（任务质量无法用确定性 oracle 判定，如「代码可读性」「方案合理性」）目前只能人工评分，无法规模化自动化。

**本项目现状**：

- `RubricSpec`（`dimensions` + `judge.model/prompt_version`）类型已定义，`CaseRevision.expect.rubric` 已挂接，但**无任何执行代码**。
- `Score.source='model_judge'`、`judge_model`/`judge_prompt_version`/`reason` 字段已预留。
- `score-write` 命令是人工评分入口，写 `scores.json`（参考分，不进硬门禁）。

**需求分析**：

1. **功能范围**：新增「rubric 裁判」执行器，对 `expect.rubric` 的开放题跑 LLM 判分，产出 `Score`（source=model_judge），落盘到 run 产物。
2. **不做的事**：不改 12 类确定性 oracle；裁判分**不进硬门禁**（与 hosted 归因「禁止 gate」同原则，仅报告）；不做 pairwise 对比（首期只做单答 rubric 评分）。
3. **关键约束（业界教训，必须遵守）**：逐 dimension 独立 LLM call（防 halo）；先给理由再判分；**上线前必须与人工标注校验一致性**（inter-judge agreement），否则不启用。
4. **依赖**：需要一个 LLM 调用通道（本项目已有 direct/hosted 模型通道可复用）；需要一个「裁判模型」配置来源。
5. **验收标准**：给定带 `rubric` 的题，能自动产出逐 dimension 的 `Score` 并落盘；裁判分与确定性 oracle 分列；与人工标注一致性达到阈值（阈值需另行对齐）。

**风险/开放问题**：

- 裁判模型选哪个、密钥从哪来（复用 `.env`？）。
- 一致性校验基准（golden 人类标注集）从哪来——这是前置条件，需先建。
- 裁判成本（每 dimension 一次 LLM call）与预算策略。

### 优化项 ②：一致性量化（pass^k / 多次 trial 范围）

**要解决的问题**：模型题（direct/hosted）结果有随机性，单次 run 的 pass/fail 是点估计，无法判断「换个 seed 是否还过」，选型结论不稳。

**本项目现状**：

- `a_flaky_rerun_delta` 指标已定义，但单次 run 记 0，且注释明说「不等于已证明无 flaky」。
- `repeats` 字段已定义，B-direct 有 `repeats` 执行（`promptfoo.ts` 里 `for repeat <= job.repeats`），但**结果如何聚合、如何报告范围，未落地**。
- `ExperimentPlan.repeat_strategy`（`repeats`/`order`/`seed`）类型已定义。

**需求分析**：

1. **功能范围**：模型题默认 `repeats ≥ 3`，报告**成功率范围（min~max）**与 **pass^k**（k 次全过的比例），而非单点。
2. **不做的事**：不改 L1/L2/L3 行为/事件题（确定性，无需 repeats）；不把 pass^k 变成硬门禁（仍是报告指标）。
3. **关键约束**：一致性必须与「同配置重跑」区分——`repeats` 是同一 run 内的多次 trial，`a_flaky_rerun_delta` 是跨 run 的重跑差异，两者语义不同，需在报告里分清。
4. **依赖**：B-direct 已有 repeats 执行，主要是**聚合与报告层**的改造；hosted 的 repeats 需评估成本（真宿主多次跑）。
5. **验收标准**：模型题跑完后，报告能给出「成功率 82%~88%（3 次 trial）」而非「84%」；flaky 题能被识别并标记。

**风险/开放问题**：

- hosted 题 repeats 的成本（真宿主 + 真模型多次跑，token/时间翻倍）——是否 hosted 也强制 repeats，还是仅 direct？
- pass^k 的 k 取多少（业界常用 pass@1 + pass^4，但成本差异大）。

> **状态（2026-10-19）**：已进入实现（ADR-0010）。grill-me 对齐结论：direct + hosted 都纳入；repeats 上移到 `RunOrchestrator.executeCase` 层循环（每次 trial 一个独立 `CaseExecution` + `Attempt`，符合 docs/02 §3.3）；B-direct 的 `job.repeats` 固定 1、`item_id` 由编排层统一追加 `::rN`；repeats 采用 **opt-in 语义**（默认 1，声明才生效，行业做法），需要稳定性结论时显式声明 `repeats=4`（业界 pass@4）；pass^k 与成功率范围纯报告、不进硬门禁。

### 优化项 ③：安全红队执行器（IPI 注入 + canary 验证）

> **状态（2026-10-20）**：已进入实现（changelog §37）。首期最小可行闭环：`proctor redteam` 命令复用 hosted 隔离机制，每个 case 注入独立随机 canary（`PROCTOR-CANARY-<hex>`），run 后程序化检测 canary 是否泄露到 stdout/stderr，产出 `security_report.json`（独立安全门禁，不进常规 pass 门禁）。**不做**：prompt judge（模型判断隐瞒）、全量红队（56 类攻击面）、对抗性自适应攻击、工作区新写入文件扫描（后续增强）。

**要解决的问题**：本项目 4.6「安全能力必须可强制执行」，但当前只有类型定义，无自动验证手段，无法证明插件在恶意输入下不会泄密/越权。

**本项目现状**：

- `SecurityBoundary.credentials.scoped_injection: true`、`canary_secret` 类型已定义。
- `FaultScenario`/`FaultInjectionProfile` 类型已定义（`scope: 'isolated'|'stub'|'proxy'`），但**无执行器**。
- 已有隔离 workspace 机制（hosted 的 `wantIsolated` + `mkdtemp` + `ensureHostedGitRepo`）。

**需求分析**：

1. **功能范围**：在隔离 workspace 注入 canary 指令（文件/材料/归档多表面），验证插件是否把 `canary_secret` 外泄或执行了注入的恶意动作。
2. **不做的事**：不做全量红队（INFUSE 的 56 类攻击面）；首期只做**间接提示注入（IPI）**这一最高威胁面；不做对抗性自适应攻击。
3. **关键约束**：注入必须在**隔离环境**执行（复用 hosted 隔离机制）；结果归因到安全维度，**独立安全门禁**，不进常规 pass 门禁。
4. **依赖**：复用 hosted 隔离 workspace + EventStore 探针；需要一个「注入点」配置（哪些文件/材料注入 canary）。
5. **验收标准**：给定注入 canary 的题，能自动判定「是否泄密/是否执行恶意动作」，产出安全维度结果。

**风险/开放问题**：

- 业界洞察「能力与鲁棒性弱相关」——安全测试必须独立于能力测试，测试集如何组织。
- 注入的 canary 如何设计才「可证伪」（避免误报/漏报）。
- 这是成本最高的一项，需明确首期最小可行范围。

### 优化项 ④：持续评测闭环（失败 → 回归题沉淀）

**要解决的问题**：回归集依赖人工增长，生产/实验中的失败模式无法自动沉淀为回归题，回归集易老化。

**本项目现状**：

- 已有 `baseline pin`/`compare`/`score-write`/`report-show` 命令。
- 项目总览 3 核心闭环第 6 步已声明「将有价值的新任务或异常沉淀为候选用例」，但**无对应命令/执行路径**。
- `Case.lifecycle` 已有 `candidate` 状态（候选），`AUTOMATION_READINESS` 已有 `not_assessed` 等状态。

**需求分析**：

1. **功能范围**：新增「异常 run → 提升为候选 Case」的命令，把失败 run 中的某题（含其 revision、oracle、证据）一键沉淀为 `candidate` 状态的新 Case。
2. **不做的事**：不做自动全量沉淀（需人工确认）；不做生产流量采样（本项目是评测平台，无「生产流量」概念，对应物是「实验/回归 run 的失败模式」）。
3. **关键约束**：沉淀必须保留**证据链**（attribution、oracle_failures、evidence_ref），否则回归题失去可复现性。
4. **依赖**：复用 `item new` 的骨架生成 + `baseline pin` 的复制机制。
5. **验收标准**：给定一个失败 run，能一键生成 `candidate` 状态的 Case 骨架（含原题 revision 引用 + 失败证据），供后续审核发布。

**风险/开放问题**：

- 「异常」如何定义（attribution 为 MODEL_* 才算？还是所有 fail 都可沉淀？）。
- 沉淀的是「原题 + 新证据」还是「新题」？语义需对齐。

### 优化项 ⑤：标准化 trace（OpenTelemetry 导出）

**要解决的问题**：自研探针无法对接业界可视化/监控生态。

**本项目现状**：全仓无 OTel 相关代码，完全未开始。

**需求分析**：

1. **功能范围**：把 EventStore/NDJSON 探针数据导出为 OTel span/trace。
2. **不做的事**：不改自研探针的归因逻辑；不做生产监控。
3. **关键约束**：OTel 导出是「锦上添花」，本项目是自研评测平台，自研探针已满足归因需求。
4. **依赖**：引入 OTel SDK 依赖。
5. **验收标准**：run 轨迹可导出为 OTel 格式。

**风险/开放问题**：

- **价值最低、成本最高**（引入新依赖 + 全链路改造），首期明确不做。

## 三、排序结论

按「价值 × 成本 × 依赖关系 × 风险」综合排序：

| 排序  | 优化项         | 价值 | 成本   | 前置依赖                         | 排序理由                                                   |
| :---- | :------------- | :--- | :----- | :------------------------------- | :--------------------------------------------------------- |
| **1** | ② 一致性量化   | 高   | **低** | 无（B-direct 已有 repeats 执行） | 成本最低、价值高、无前置依赖，先做可立即提升选型结论可信度 |
| **2** | ① 裁判模型     | 高   | 中     | 需先建「人类标注校验基准」       | 补开放题自动化，但前置条件（校验基准）需先建               |
| **3** | ④ 持续评测闭环 | 中   | 中     | 复用已有命令，无硬依赖           | 补题库演进，成本中等，可与①②并行                           |
| **4** | ③ 安全红队     | 高   | **高** | 依赖隔离机制（已有）+ 注入设计   | 对应硬性要求（4.6），但成本最高，需先明确最小可行范围      |
| **5** | ⑤ OTel 导出    | 低   | 高     | 无                               | 价值最低，明确后置                                         |

**建议工作链路顺序**：② → ① → ④ → ③ → ⑤

**理由**：

- ② 一致性量化是「低垂果实」，先做能立即见效，且为后续 ①③ 的「可复现性」打底（裁判模型和安全红队都需要多次 trial 才能证明稳定）。
- ① 裁判模型价值高，但**前置条件是建人类标注校验基准**，需先单独对齐这个基准怎么建。
- ④ 持续评测闭环与 ①② 无强依赖，可并行，但排序靠后是因为它解决的是「题库老化」而非「当前评测质量」。
- ③ 安全红队对应本项目硬性要求，但成本最高、需先明确范围，放后面单独立项。
- ⑤ 明确后置。

## 五、2026-10-19 对齐进展：优化项 ① + 全面界面化

经 grill-me 对齐，方向升格为「全面界面化（宽口径）」，优化项 ①（裁判模型）作为第 0 期载体落地。

- **界面形态**：从终端 console 升级为现代化 Web 界面（复用 `src/` 领域层 + run 引擎，外包 HTTP API + SPA），console 逐步退役。见 ADR-0009。
- **全局模型配置池 `models.json`**：`Provider`/`ModelCatalogEntry` 的可维护配置实例，扩展 `category`（单值主分类）、`tags`（多值筛选）、`params`（参数档）、`api_key_env`（密钥引用）。这是裁判模型与完成任务模型的共用配置来源，也是优化项 ① 的前置依赖。
- **裁判体系三类来源**：题目对比（确定性 oracle，必现）、模型判断（LLM-as-judge，人为触发）、人工判断（human，人为触发）。三类 `Score` 分列、不进硬门禁。
- **分期**：第 0 期（本次，Web 骨架 + `models.json` + 裁判体系）；第 1 期（录题/环境/数据集界面化）；第 2 期（跑批/报告/健康检查界面化 + console 退役）。

> 注：优化项 ① 原排序依赖「先建人类标注校验基准」，本次按用户口径调整触发语义（模型判断改为人为触发而非 run 内自动），校验基准的建立留待模型判断上线前单独对齐。
