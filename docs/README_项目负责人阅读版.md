# AITestTools 项目说明（阅读版）

> **阅读对象：** 项目负责人、产品/测试设计人员、架构与开发人员、评审人员  
> **用途：** 先快速理解项目要解决什么问题、使用流程是什么、关键概念如何区分，再进入正式需求和设计文档。  
> **规范地位：** 本文件是阅读导览，不替代正式规范。具体需求以 `01_产品需求规格说明书.md` 为准；对象、状态、指标、配置和技术契约以 `02_总体架构与领域设计.md` 为准。

## 1. 用一句话理解项目

**AITestTools 是一个面向真实 Agent 工作任务的黑盒自动化评测平台。** 它把真实任务整理成可维护、可复现、可自动执行的测试用例，再用一致的测试条件比较万象术等插件/配置对任务完成质量、耗时、Token 和费用的影响，并保存足够的运行证据供复核和回归。

它不只是“批量运行脚本并生成报告”，更重要的是形成持续循环：

**整理任务 → 形成测试用例 → 组成测试集 → 配置实验 → 建立环境 → 执行并留证 → 评测比较 → 异常沉淀为新用例 → 回归复用。**

## 2. 项目要回答的核心问题

首轮核心实验是在相同任务、相同模型和约定一致的条件下，比较使用万象术与不使用万象术时的差异。主要围绕三类指标分别报告：

- **快：** 单个任务耗时、整批执行耗时、从启动到最终报告封存的端到端耗时。
- **好：** 任务是否完成、预期条件是否满足、Rubric 各维度得分，以及必要时的人工作用评分。
- **省：** 输入/输出/总 Token、调用量和费用；费用必须说明是真实计费数据还是按价格表估算。

平台不预设“开万象术一定更好”。结果可能是质量提高但耗时增加，也可能节省 Token 但质量下降。报告应分别展示这些取舍，而不是在没有约定权重时合成一个看似精确的总分。

## 3. 从使用者视角看完整流程

<ol>
<li><strong>准备测试用例。</strong> 写清任务目标、输入材料、前置条件、预期结果、判定办法、证据和清理要求。可以从人工巡检、历史异常或已有任务中导入，再补齐为正式用例。</li>
<li><strong>发布测试集。</strong> 审核用例和判定规则，将确切的用例版本组成不可变的数据集发布版本，避免实验开始后修改预期。</li>
<li><strong>配置实验条件。</strong> 选择 Host/Agent、Provider/模型或模型等级、万象术是否加载、受支持的 Profile、预算、环境和并发/重试策略。</li>
<li><strong>检查配置与环境。</strong> 检查版本、配置入口、依赖关系、密钥引用、预算、平台兼容和安全隔离。界面可以先显示模拟路由，但会明确模拟结果与真实运行的区别。</li>
<li><strong>一键运行并观察。</strong> 建立或复用符合条件的独立环境，执行任务；界面展示 Agent 工作链路、当前状态、模型/工具调用、日志、异常和证据。</li>
<li><strong>自动评测与比较。</strong> 依据已冻结的 Oracle、Rubric 和人工评分，汇总任务结果、时间、Token、费用及可比性限制。</li>
<li><strong>整理新发现。</strong> 将运行中发现的异常或有价值的任务转成候选用例；经过脱敏、复现、明确预期、验证判定规则和审核后，发布到后续回归集。</li>
</ol>

## 4. 最重要的概念：56 个 package 不是 56 个开关

万象术的功能/消融资源包含 package、slice 等目录节点，以及节点关系和命名 Profile。它们可以帮助测试平台展示“被测版本定义了哪些模块/规范包、这些节点如何关联、有哪些现成的配置组合”，但不代表每个节点都提供了独立的外部控制参数。

需要始终区分：

| 概念            | 通俗解释                                      | 平台如何处理                                             |
| --------------- | --------------------------------------------- | -------------------------------------------------------- |
| 功能/规范包目录 | 被测版本中的模块/节点清单                     | 展示节点、来源、版本与关系；目录本身不是开关面板         |
| 默认行为        | 万象术按代码、资源和预设规则正常运行          | 没有独立控制入口时，通过合适任务观察实际行为             |
| 外部控制点      | 版本真实支持的配置项、环境变量或接口          | 只有核实后才能作为可操纵的实验变量                       |
| 命名 Profile    | 万象术预先定义的一组节点状态组合              | 可比较该版本真实支持的 Profile，不推断每个节点都能单独改 |
| 测试用例        | 让 Agent 实际完成的任务                       | 决定测什么、预期是什么、怎样判定结果                     |
| 实验配置        | 本轮选用的用例、模型、Profile、环境与运行策略 | 在运行前冻结；每次运行保留自己的快照                     |

**举例：** 如果目录中有一个与子 Agent 委派有关的节点，但当前版本没有公开该节点的独立配置入口，平台可以设计需要多 Agent 协作的任务，并观察真实调用链；不能自己生成一个“委派开/关”参数，也不能只凭任务表现把变化归因于该节点。

功能配置页应帮助人一眼看出“完整节点目录”“真实可操作的控制点”“当前 Profile 的节点状态”不是同一回事。

![功能配置页示意](assets/feature-config-wireframe.png)

可用的实验方式因此分为几类：

1. **整体 ON/OFF：** 比较万象术整体加载与不加载。
2. **命名 Profile 对照：** 比较被测版本本身支持的预定义配置组合。
3. **单项消融/组合实验：** 仅在确有受支持、可验证的单项控制入口时使用；依赖和借用条件必须满足。
4. **默认行为观察：** 对没有独立外部控制项的节点，用真实任务检查它的可观察行为，不声称做了单项开关实验。
5. **源辅助变体：** 如果实验直接修改了 Profile 资源或源码，应记录新的 commit/hash/构建信息，单独报告，不与未修改版本的黑盒基线混为一谈。

配置页面因此既要展示完整目录，也要明确标出每个条目的控制方式与证据：可配置、仅能选择现成 Profile、默认行为/仅观察或未知。**不能因为资源文件里存在一个状态字段，就认为它一定是运行时可操作的独立开关。**

## 5. 测试集与实验怎样保证可比较

### 5.1 同测试集、同模型

ON/OFF 对照应引用同一个发布版测试集和同一套判定规则；基准实验固定 Provider、模型、角色路由、关键参数和环境约束。万象术导致的真实 Agent 调用变化属于被观察对象，应记录下来；未声明的模型或环境配置漂移则要披露，必要时降低结论等级或阻断比较。

### 5.2 任务类型和难度

测试集不应只由一种简单任务构成。应按任务类型、难度和能力需求组织覆盖，例如代码理解、缺陷定位与修复、功能开发、重构、测试编写、约束遵循和异常恢复等。具体分类以正式用例库为准。报告既要显示总体结果，也要能下钻到任务类型、难度、模型等级和具体用例，防止总体平均值掩盖某类任务明显变差。

### 5.3 模型分层

模型可以按能力/质量档、成本档或项目定义的其他维度分层；这些等级属于可维护的配置，不应将某一份固定模型名单写死在核心规范。对每个模型层，优先在同一模型和同一任务条件下完成 ON/OFF 配对。不同模型之间的结果用于横向分析，不代替同模型对照。

### 5.4 质量判定

每条正式用例需要定义可检查的预期和判定方式。机器判定适合明确的结果条件；开放式任务可使用事先定义的 Rubric 和人工评分。人工评分要保留评分者、量表版本及分歧信息；不能因为评分难，就把模型输出“看起来不错”直接算成通过。

## 6. 可视化界面应帮助用户看懂什么

建议的主要页面包括：

- **总览仪表盘：** 当前实验、运行状态、成功/失败/无法判定数量，以及快、好、省概况。
- **功能目录与配置：** 展示万象术节点、关系、配置方式、命名 Profile 和验证状态；模拟路由与实际路由分开展示。
- **测试用例管理：** 按类型、难度、能力和状态查询用例，查看输入、预期、Oracle/Rubric、版本与审核记录。
- **环境管理：** 选择环境配方，一键创建、检查、重置、停止和销毁；查看环境实例、依赖、版本与清理记录。
- **Agent 工作链路：** 展示真实父子 Agent/角色、模型与工具调用、事件顺序和关联日志；没有真实事件的节点不得伪装成已发生。
- **运行详情：** 逐 Case 显示执行状态、Attempt、产物、Token/费用、失败原因和证据完整性。
- **对比分析：** 在同一测试集和协议下比较 ON/OFF 或 Profile 之间的差异，提供按任务、难度、模型层和指标下钻。

## 7. 独立、可重建的测试环境

AITestTools 自身需要用独立 Git 项目管理代码、需求设计、配置模板、测试资产、环境配方与验证工具；万象术作为独立被测仓库或固定版本依赖，不把被测插件代码直接合并进测试工具核心。

环境分为两类记录：

- **环境配方（EnvironmentProfile）：** 描述如何创建环境，包括 OS/运行时要求、依赖锁、Host/插件版本、工作区模板、权限和隔离策略。
- **环境实例（EnvironmentInstance）：** 记录某次实际创建的环境及其版本、状态、配置哈希、输入数据、运行关联和清理结果。

一键创建不只是“安装成功”；还应完成版本和能力检查，并能记录失败原因。已销毁的实例可根据配方重建，但远程 Provider、在线模型或外部数据可能不能做到完全确定性复现，这些限制应明确记录。环境可复建也不自动代表具备安全隔离能力，两者要分别检查。

## 8. 异常和非功能测试不是附属项

测试平台还要检查网络和各执行环节异常时，系统是否安全、可解释、可恢复。至少考虑 DNS 失败、连接超时、提交后断连、限流、服务端错误、慢响应、usage 缺失，以及 Host/插件加载、Agent/工具调用、日志/Artifact 采集、评分、持久化崩溃、取消和进程清理等场景。

每个故障场景应说明注入方式、预期错误类别、是否允许重试、预算处理方式、运行终态、所需证据、清理动作和副作用核对。可能重复产生副作用的请求不能盲目重放；不可安全修复时应明确提示人工介入，而不是无限重试。

## 9. 首期交付的边界

首期需要形成完整可核验的纵向闭环：用例管理与发布、整体 ON/OFF 对照、真实插件状态证据、独立环境、受控执行、证据采集、结果评价、配对比较和异常用例沉淀。Windows、macOS、Linux 均为目标平台；每个平台正式声明支持前，必须有真实任务执行闭环和所需安全隔离的验证证据。

首期不要求一次性维护世界上所有模型和用例，也不要求自动生成全部测试代码、进行完整的 2^N 全因子探索或建设分布式多租户平台。平台应提供可演进的数据结构和扩展接口，清单可以逐步添加；一次正式实验则必须把实际选择的配置和版本固定下来。

## 11. 设计取舍的原因

- **用例与配置分离：** 同一个任务可以重复用于多个模型和功能配置；如果把配置写死在用例里，就难以做公平对照和长期复用。
- **计划、实际事实与结论分离：** 配置中写了什么不等于运行时确实生效；计划路由、实际调用事件和最终评价必须各自保留。
- **不可变发布和运行快照：** 历史实验要能解释和复现；新版本可以持续演进，但不能悄悄改写既有结果的输入条件。
- **真实能力优先于界面便利：** 没有真实控制入口就不做假开关；无法强制的预算不标成硬上限；没有证据的调用链不伪造为实际发生。
- **先完成端到端闭环，再逐步扩展：** 这能优先验证平台最重要的价值，同时避免首期被穷举组合、全自动评分或分布式部署等高复杂度目标拖住。
