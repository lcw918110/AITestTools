# 首期实验方案与用例治理（V2.17）

本文件统一规定首轮研究问题、ON/OFF 对照、快好省口径、实验有效性判断以及用例库如何从真实任务中持续成长。它不记录实际实验结果；所有输出结果只能在实际执行后填写。

## 1. 首轮主实验

### 1.1 研究问题

在同一组任务上，比较以下两个条件：

- **ON：** 目标 Host 实际加载了所测版本的万象术插件；
- **OFF：** 目标 Host 实际没有加载该插件。

核心问题是：在声明的 Host、Agent、模型和权限条件下，启用万象术与不启用万象术相比，整体任务运行是否更快、任务质量是否更高、Token/费用是否更省。实验不预设 ON 一定获胜。结论的直接归因范围是“这组固定条件下 ON 与 OFF 的系统表现差异”；只有在除插件状态外的影响因素确实固定或可解释时，才可以进一步讨论差异是否由插件状态造成，不能将其扩大为对所有模型、任务或平台的普遍结论。

OFF 必须由 Host 或其他独立运行证据确认，不能只看配置文件、下拉框或文件是否存在。若目标版本无法形成合法且可核验的 OFF 条件，就不能伪造基线或宣称插件净效果；原始数据可用于诊断，但正式 ON/OFF 结论保持未成立。

### 1.2 固定条件与变化因素

默认只有一个主动变化因素：万象术插件加载状态。对照两边尽可能固定：

- Host/OpenCode、Agent 与角色配置；
- Provider、模型/部署、参数与预先声明的 fallback 策略；实际发生的调用路径单独作为观测事实记录。
- Case/Dataset Release、任务输入与材料；
- Oracle/Rubric/评分器版本及其调用配置；
- OS/运行时版本、工作区起始状态、权限/网络边界；
- 预算、超时、重试、并发、缓存/预热和清理策略；
- 计时边界、usage 采集器/版本与 Artifact 采集方式。

任何不能固定或无法观测的字段，都要列为差异/限制。这里固定的是路由策略、模型参数和允许的 fallback 规则，不是强迫两边运行时出现完全相同的调用轨迹。万象术开启后若触发额外的子 Agent/角色调用或改变实际工具路径，该差异本身可能正是插件的行为效果，应记录到结果并计入对应任务的耗时/Token/费用；不能因其与 OFF 的实际轨迹不同就自动判定不可比。若实际调用偏离已冻结策略（例如未经允许的 Provider fallback），或需要作模型身份归因却无法确认实际身份，则按相应结论范围降级/阻断。ON/OFF 两边应对等重置工作区、会话和任务外部状态，避免第二个任务继承第一个任务的产物。

### 1.3 实验顺序和重复

比较以相同 Case 的配对运行为基本单位，保存稳定 `pair_key`。条件允许时使用随机或平衡顺序，减少顺序、缓存和服务负载偏差；如果不能做到，报告要披露风险。默认建议每个 Case/条件做 3 次独立重复，允许因探索目的或成本约束调整。只运行一次时，报告只能描述这一次观测，不推断稳定的普遍优胜。

重复数必须提前声明，不得看到结果后只保留有利的一次。技术重试不是独立重复；重试消耗纳入成本和耗时，但不增加统计样本量。Windows、macOS、Linux 的结果首先按 OS/版本组合分层报告；只有预先说明跨平台汇总的理由、条件与异质性处理后，才可以给出合并结果，不能把某个 OS 的 ON 优势直接概括为所有平台都成立。

### 1.4 功能级消融与组合实验

功能目录以固定万象术版本的 `resources/ablation/nodes.json`、`profiles.json`、`fact-map.json`、`tool-map.json` 为来源，并核对实际运行入口、默认行为和可观测证据。参考 commit 的 `nodes.json` 中有 56 个 package 节点和 3 个 slice 节点；这里的 56 是消融拓扑中的目录节点数量，不是 56 个外部开关，也不是 56 个可直接独立操控的实验变量。产品必须分开管理“节点目录”“真实外部控制点”“已有命名 Profile”“默认行为”与“实验干预”。

这五者的关系可以理解为：**目录列出“有哪些节点”；默认行为说明“不额外配置时怎样运行”；外部控制点说明“用户实际能改变什么”；Profile 说明“项目方预先提供了哪些状态组合”；实验干预说明“本次实验真正改变了哪个受支持的控制”。它们不是同一张表的不同列，也不是一对一关系。

固定版本 README 公开的 `WANXIANGSHU_ABLATION_PROFILE` 是命名 Profile 选择入口；`profiles.json` 是这些 Profile 的状态组合。某 Profile 中为每个节点记载 `active / borrowed / ablated`，表示该 Profile 下节点状态，不自动证明测试平台可以在运行时任意覆盖单个节点。只有通过目标版本真实接受的控制接口表达、并在执行中证明生效的变化，才能作为正式干预。默认配置下内置的行为应按版本和资源记录，不另造外部参数。

功能相关实验分为以下类型：

0. **默认行为/黑盒场景基线：** 在未额外覆盖功能配置的标准安装/默认配置下，使用覆盖不同任务类型和难度的测试集，观察任务完成情况、产物质量、实际链路、耗时和 Token/费用。按 `requirements/` 或节点映射组织覆盖，但不能仅由映射关系推断某个包已被单独触发。
1. **整体 ON/OFF：** 固定同一测试集、模型/路由策略和环境协议，只改变插件是否加载；完整记录 ON 侧实际默认 Profile/配置快照。
2. **已有命名 Profile 对照：** 比较当前版本真实提供且能通过公开入口选择的 Profile。若多个节点状态同时变化，归因于 Profile/候选组合差异，不归因到其中任何一个单独 package。
3. **单项启用/消融：** 仅当节点有经验证的独立运行时控制点或目标版本明确支持的单项测试接口时开放；固定其他变量，验证控制值确实进入运行，并确认实际状态/行为证据。不能单独控制的节点不生成单项实验。
4. **依赖顺序累积/交互实验：** 仅当每一步组合都可以通过受支持控制方式表达，并经源版本规则校验、生效证据确认后执行。若必须改写安装包内的 Profile 资源或源码才能实现，应标成“源辅助变体”，冻结新 commit/hash 和构建信息，与未修改版本的黑盒结果分开报告。
5. **源辅助变体：** 只有当研究问题确实要求改变原版未暴露的内部节点状态，且已获准修改 Profile 资源/实现时才采用。该实验必须固定变体的新 commit、资源/构建 hash、差异清单和运行方式；与未经修改的默认行为及原版 Profile 对照分开报告，不将它包装成原版黑盒运行。

功能配置 UI 不得把 56 个节点自动渲染为 56 个可编辑开关。它应显示控制能力类别、默认行为来源、可选 Profile/入口、实际生效证据与归因范围。任何节点状态假设都必须标记为“可执行候选”或“假设性模拟”；后者不能直接运行，也不能用于单项归因。

源关系图必须保留边类型并分别解释：`station-order` 是源定义的顺序约束；`borrow` 是与 `active / borrowed / ablated` 状态相关的借用前置条件，不等同于普通硬依赖。固定版本契约规定：对 `station-order` 边，仅当 `to=active` 时要求 `from` 为 `active` 或 `borrowed`；对 `borrow` 边，当 `to=borrowed` 或 `to=active` 时要求 `from` 为 `active` 或 `borrowed`。实际实现和固定版本校验器是最终语义依据，需以契约测试验证，不得只按边名猜测。通用硬依赖要有源 Profile、Schema 或实际实现证据。源 `station` 值可能重复或缺号，拓扑结果需要稳定的平局消歧策略。目录导入必须对账同一 commit 的 nodes、profiles、requirements 目录和实际实现，并报告无法映射的节点/目录。在生成矩阵之前，系统执行源边分类、借用前置条件、经证实的依赖/互斥和合法状态校验，显示预估候选数、任务/模型层覆盖、独立重复数、预计时间/Token/费用与未覆盖节点。若一个节点无法独立控制，按依赖组合或 observational-only 处理，报告不把它的结果归因为单项开关差异。模拟路由在正式执行前产生并冻结；运行后以真实 AgentInvocation/Event 路径与其对照。

### 1.5 模型等级与任务类型/难度的分层比较

模型分层标签应由配置定义，至少允许表达质量/能力导向、均衡、低成本等常见选型。分类名称和成员可维护，不预设固定模型名单。每个层内 ON/OFF 对照保持同一具体模型/Deployment/参数与 fallback 策略；跨层报告每个模型的插件增益/退化及成本变化，不把层间模型差异当成插件效果。

DatasetRelease 必须可以报告 `task_type × difficulty_level` 覆盖。难度可采用项目定义的有限有序等级，但每一级须有判定准则或标注依据；正式比较固定版本的标签。报告除总体快/好/省外，应支持按任务类型、难度、模型等级、功能配置筛选和下钻，显示有效配对数、缺失与协议偏离。

## 2. “快、好、省”指标定义

### 2.1 快：整体时间更短

时间必须分成不同作用范围，不能把整批耗时、单题耗时和平台开销混为一个数：

1. **首要整体指标 `run_end_to_end_wall_time`：** 从系统成功接受启动请求（开始 Preflight 之前）的时间点，到该 Run 的所有计划项获得明确终态、清理阶段结束并封存 RunFinalManifest 的时间点。它表示用户从点击启动到取得最终报告的总耗时，包含 Preflight、准备、批次排队/调度、执行、技术重试、证据采集、评测、清理与封存。若 Preflight 阻断且没有进入正式执行，单独报告启动检查耗时；该 Run 不纳入正常性能配对，但保留在平台可用性/阻断率报告中。
2. **执行批次指标 `batch_execution_wall_time`：** 从该 Run 第一个纳入计划的 CaseExecution 进入执行队列的事件时间点，到最后一个目标 CaseExecution 达到执行终态的时间跨度。它包括批次内排队/调度、Provider 等待和执行重试，但不包括 Preflight、最终评分/证据整理/清理/封存；Case 评测耗时单独记录。这样初始排队是否被计入不会因候选而改变。
3. **单 Case 指标 `case_elapsed_wall_time`：** 从某个 CaseExecution 首次尝试开始，到该 CaseExecution 最终执行终态的时间，包含其重试间隔；单次 Attempt 的时长另行记录。
4. **平台开销：** 预检、环境准备、证据整理、评分、清理和报告生成分别报告，不重复计入 `case_elapsed_wall_time`。整体指标是否包含这些阶段已经由 `run_end_to_end_wall_time` 明确包含，不能在不同候选中改变口径。

每项耗时都使用单调时钟记录起止事件、单位和采集器版本；用于跨进程/跨 Run 排序的 UTC 时间应与单调耗时分开保存，避免墙钟校时造成负耗时或错误排序。正式比较要求同一计时边界、相同计划并发与相同流程配置。批次整体比较以同一 Experiment 区组下的 ON/OFF Run 配对；逐 Case 比较使用相同 `pair_key`，先计算配对差，再报告中位数/P90和有效配对数。批次墙钟时间回答“整批总共多长”，不能用单题平均耗时代替，也不能把高并发吞吐误称为单任务延迟。

### 2.2 好：任务质量更高

质量至少报告三个层次，不能把不同含义合成一个未解释总分：

1. **计划范围成功产出率 `planned_success_yield`：** 按 `02_总体架构与领域设计.md` §5.2 的权威公式计算。纳入计划但被阻断、未运行、执行失败、超时、取消或无法判定的项目仍留在计划分母中，体现整个系统在约定范围内产出合格结果的能力。
2. **已判定通过率 `evaluated_pass_rate`：** 同样采用 02 §5.2 的权威公式，只表示已明确判为通过/失败的样本，不代表完整计划任务的成功概率；必须同时显示判定覆盖率及 indeterminate/not_evaluated 数量。
3. **Rubric 质量：** 对开放式任务按预先定义的维度（目标满足、正确性、完整性、工具使用合理性、约束遵循、交付产物质量等）分别报告分布。每个维度需有量表、方向、评分者来源、适用样本与版本。只有当评分量表和聚合公式在实验前明确定义时，才可显示维度总分；默认不构造隐藏加权平均。

ON/OFF 必须使用同一版 Oracle/Rubric 和相同判定规则。适用时对人工评审/裁判隐藏 ON/OFF 标签。模型裁判未经独立校准时标为未校准；其分数不能伪装成客观真值。对通过/失败率，除总体率外，优先提供同题配对转移表（OFF fail → ON pass、OFF pass → ON fail 等），避免仅比较两个总体百分比而丢失同题变化。

### 2.3 省：Token 更少、费用更低

至少分别记录：input tokens、output tokens、total tokens、Provider 调用数、fallback/子 Agent/不同角色调用、重试消耗、价格版本及估算/实际费用。被测任务的消耗与评分器自身的消耗应分开显示；如同时展示整次实验的总费用，应说明计入了哪些部分。

- 优先使用 Provider 或 Host 实际返回的 usage；不可观测时标 `unknown`。
- 按价格表计算的成本是估算值，需标明 Provider、模型/部署、币种、价格版本和估算公式。
- 实际账单与估算费用分开，不得把缺失 usage 或费用填成 0。
- 如果 Token 可测而价格缺失，仍可比较 Token，但成本结论必须标“未知/不完整”；不得宣称完成了完整的省钱比较。

### 2.4 比较公式和展示规则

每条 `MetricSpec` 必须预先冻结作用范围、单位、起止边界、分子/分母、聚合方法、有效配对条件、缺失处理和方向。最少提供以下可复算结果：

- **Run 整体时间节省率：** 仅对有效的 ON/OFF Run 配对计算 `(T_OFF - T_ON) / T_OFF`，其中 T 必须是同一个已声明时间指标；`T_OFF <= 0` 或有一侧缺失时不可计算。
- **Case 时间差：** 对每个 `pair_key` 分别计算 `T_ON - T_OFF`（越小越快），再对有效配对差给出预声明的中位数/P90或其他已声明聚合；不能先把不同 Case 时间混成一个未解释比例。
- **通过率差：** `planned_success_yield_ON - planned_success_yield_OFF` 与 `evaluated_pass_rate_ON - evaluated_pass_rate_OFF` 分开展示，并同时显示各自分子、分母及判定覆盖率。
- **Rubric 质量差：** 每一维度按同版本同量表比较配对得分差；只有在预声明的评分规则允许聚合时才显示量表合计。
- **Token 节省率：** 仅当配对两侧都具备同口径可靠 Token 数据且 OFF Token 大于 0 时，计算 `(Tokens_OFF - Tokens_ON) / Tokens_OFF`。插件引起的额外子 Agent/角色调用纳入被测任务消耗；评分器自身调用单列。
- **费用差/节省率：** 仅在两侧价格版本、币种、费用范围一致且来源足够可靠时计算。估算费用与实际账单分开，不能混算。

所有指标应显示 `N_planned`、`N_valid_pairs`、`N_missing/unknown`、排除数和覆盖率。不同指标的有效样本可能不同，不能用同一个 N 掩盖缺失。基线为 0、数据未知、配对不成立或条件不匹配时显示不可计算/受限原因，而不是填 0 或生成误导性百分比。首期主要提供描述性比较；若没有预注册的统计检验与足够样本，不使用“统计显著”措辞，也不把 3 次重复自动解释为普遍结论。

## 3. 什么叫首轮实验通过

必须分三个层次，不能用某一个“成功率”替代全部判断。

### A. 平台执行有效性

所有预先声明纳入范围的工况都必须有真实、可解释的结果：要么完成执行并产生所需证据，要么按照预先声明的负例/阻断规则明确停止并记录原因。任何 Case 都不能静默消失或被算作通过。目标 OS 的平台能力不能用另一个 OS 的成功结果代替。

“各种工况能运行”不等于每个任务的业务结果都必须通过。例如，某个负例的预期就是拒绝越权操作，系统正确拒绝才是任务通过；某个 ON/OFF 条件下目标行为无法完成，也要区分是实验条件下的业务结果，还是任务从未真正执行。

### B. 比较数据有效性

- ON 与 OFF 使用同一冻结用例和约定条件；实际插件状态有证据。
- 计划范围、执行范围、配对关系、重复策略、排除规则和协议偏离清楚。
- 时间边界相同，质量判定规则相同；Token/费用来源明确，unknown 不当作 0。
- 每个纳入范围的 Case 都有终态，或有显式的 blocked/not_run/indeterminate 说明。
- 关键条件偏离时，Comparability Gate 按预先规则降级为受限/探索性/阻断。

### C. 插件效果结论

通过 A 和 B，表示平台完成了一个有效的对照实验，不代表 ON 必须胜过 OFF。结果可以是 ON 更好、OFF 更好、不同指标互有取舍或证据不足。正式结论必须分别表达时间、质量、Token/费用，并说明适用任务、样本规模、波动与限制。

若某项主指标缺乏可信数据，则报告可以说明部分结论成立，但不能宣称完整的“快、好、省”三项比较已经全部完成。指标结果不佳不是平台测试失败；无法保证条件一致或关键数据不可观察，才是比较有效性问题。

## 4. 用例库的持续维护设计

### 4.1 用例生命周期

`draft → candidate → reviewed → validated → released → deprecated`

- **Draft：** 新建中的用例，合同/细节尚不完整。
- **Candidate：** 来自实验发现、历史异常或人工巡检的候选；还不属于正式回归门禁。
- **Reviewed：** 预期行为、边界与风险经过人审，评分规则方向明确。
- **Validated：** 可复现性、Oracle/Rubric 和所需证据经过验证。
- **Released：** 进入一个不可变 Dataset Release，可用于正式运行。
- **Deprecated：** 不再默认选用，但历史 Release 与 Run 仍可复核。

`Case` 是稳定逻辑身份；每次正式规格内容由不可变 `CaseRevision` 表达。Release 不可原地修改。改变输入、预期、材料或 Oracle 应生成新 CaseRevision/Release，并记录差异及适用范围。

用例正式生命周期与自动化准备度必须独立维护。自动化准备度（与生命周期状态分开的字段）建议值为 `not_assessed / manual_only / spec_incomplete / design_ready / blocked`。在宣称“可自动执行”前，应具备前提条件、动作/步骤、输入材料、预期合同、Oracle/Rubric、所需证据、初始化/清理与权限边界；任何一项缺失都应显示为待补齐/受阻。该准备度用来协助测试设计和维护，不代表实现进度，也不代表执行结果通过。自动执行计划只能纳入在 Plan 冻结前已声明为本次范围且满足执行条件的用例。`manual_only`、`blocked` 或未达到 `design_ready` 的用例，不得被静默计入计划执行范围；若计划明确选择它们作为排除项，应在运行前留存排除原因，不能事后为了改善通过率调整分母。

### 4.2 从实验到回归库的闭环

`Run 发现问题 → 选取相关事件/证据 → 脱敏 → 初步分类 → 指纹去重 → 复现/最小化 → 确认预期合同 → 编写或更新 Oracle/Rubric → 自测试 → 独立审核 → 发布新版本 → 加入回归集合`

异常至少可初分为：产品问题、预期负例、环境问题、Provider 错误、测试数据问题、随机/不稳定结果、设计待决和未知。只要合同或证据尚不确定，就保留为 Observation 或候选，不以增加用例数量为目的降低入库门槛。

### 4.3 首轮锚定用例的角色

建议先选 3–5 个高价值锚定 Case，至少覆盖：

1. Host 对万象术 ON 状态的真实加载确认；
2. 一个真实、有限且可评判的小任务；
3. 一个约束/负例或边界行为；
4. 一个证据缺失或异常归类场景；
5. 一个超时/取消/清理场景（若可与前项合并，可以减少 Case 数）。

最终用例输入、预期、权限和 Oracle 需由产品/测试人员确认。本清单只是候选覆盖指导，不代表现有测试已覆盖，也不意味着首轮完成后用例库就结束建设。

## 5. 多 Provider 与模型池的实验要求

同一个 Agent 的不同角色可以绑定不同模型；一个 Provider 也可以提供多个模型/部署。模型池通过能力和角色需求给出候选，路由冻结后用于实验。对首轮 ON/OFF 实验，默认应固定 Provider、模型、角色路由和参数，只改变插件状态；若同时改变模型路由，则实验只能归因于整个候选组合，不能把差异单独归因于万象术。

实际调用应尽可能记录模型/Provider/角色/回退、usage 与请求 ID。预算默认汇总被测任务链路中的全部角色/子 Agent、fallback 和技术重试，评分器/观察器成本单列；若选择将评测成本并入预算，必须在 Plan 冻结时明确声明。计划路由策略与允许 fallback 是固定条件；实际路由轨迹是观测事实。若 ON/OFF 因被测插件行为而产生不同数量的角色/子 Agent 调用，该差异属于效果机制，必须保留并计入消耗；若因未经声明的配置漂移发生不同 Provider/模型路由，则记录为协议偏离，并根据结论是否依赖相同模型身份来降级/阻断。模型选择值与真实调用值不同或不可观测时，必须披露差异并调整比较结论等级。

## 6. 预算、异常和 Artifact 策略

### 6.1 预算

采用 `default-large-finite` 一类的宽松但有限配置档。生成策略和参数均可版本化、可替换；算法必须给出确定的输入优先级、有限值推导、缺失输入处理与每字段来源，不能只写“根据资源自动计算”。建议的首期生成规则如下：

1. **统一上限优先级：** 生效硬上限不得高于用户明确上限、已知 Provider/Host 硬限制和当前策略安全上限中最严格的一项；若某来源只是文档建议/软限额而非可执行约束，需标记其强制能力。
2. **时间与并发：** 有足够同类历史观测时，可按同一运行配置/任务类别的历史高分位值乘以版本化余量系数生成建议，并受可配置绝对上限约束；没有历史样本时，使用策略中明确配置的有限基准值并要求确认，不能从 CPU/内存直接推导任务耗时。
3. **Provider 调用与 Token：** Provider 已知的硬累计请求/用量配额可约束 Run 上限；请求速率限制只约束速率/并发，不可直接等同于整次 Run 最大调用数。模型上下文窗口只约束单次请求的输入/上下文上限，不能直接充当整次 Run 的累计 Token 上限。`max_total_tokens` 是 Run 内累计 Token 总量的聚合硬/软边界；`max_input_tokens` 与 `max_output_tokens` 是各自累计输入、输出 Token 的子边界，不是单次请求上下文上限。三者由可配置有限策略、已验证的 Provider 累计限额与同类历史 usage 高分位/余量规则共同解析；缺少历史数据时使用显式有限策略基准并要求确认。配置校验要求：若设置了 `max_total_tokens`，则任何已设置的输入/输出子边界都不得大于总边界；输入与输出子边界之和可以大于总边界，因为总边界会先限制两者的组合累计量，不要求将两个子边界简单相加作为总量。校验失败必须在 Preflight 前要求修正，不得静默裁剪。实际 usage 的口径、可观测性和延迟须按 Provider 记录；若 usage 缺失/延迟，必须将 Token 强制级别降为实际可证明的 `soft/unknown`，并用可强制的调用数/时间等边界提供保护。不得把机器资源或单请求上下文窗口直接当成累计 Token 消耗的估算依据。
4. **费用：** 仅在价格来源、模型/部署、币种与 Token 上限可确定时估算；优先按各角色/可能 fallback 路径的受控上界估算。必须区分**费用预算上限**与**运行前费用预测值**：前者是用户/策略设置的预算边界，后者是基于价格和预计调用量的估计输出。若费用不可可靠估计或 Provider 不支持真正的硬预算强制，应把该预算的 `enforcement_mode` 标为 `soft/unknown`，要求用户确认并通过调用数/可观测 Token/时间等可执行上限提供二级保护，不声称“费用硬封顶”。
5. **Artifact 配额：** 先计算 `headroom_for_new_writes = max(0, current_free_disk_bytes - system_reserve_bytes - failure_metadata_reserve_bytes)`；在不超过策略 ceiling 的前提下，按可配置分配比例得到新增写入空间。若配置的是全局总配额，则 `effective_store_quota = min(policy_ceiling, current_store_used_bytes + allocated_headroom)`，可继续写入量为 `max(0, effective_store_quota - current_store_used_bytes - active_reserved_bytes)`。单 Run 与单文件限额不得超过剩余可用分配；须为终态、失败记录和最小清单预留保底元数据空间。并发写入应通过配额预留避免超卖；自动过期默认关闭。
6. **逐字段强制级别与缺失/冲突：** 每个预算字段都需声明 `hard / soft / unknown` 强制级别和依据。例如墙钟时间可由监督器强制；累计 Token 只有在调用/usage 观测足够时才能可靠封顶；费用通常只有 Provider 明确支持硬限制时才可标 `hard`。`soft` 表示可能在一次调用完成后才发现超限，必须披露潜在超出幅度并用可强制的调用数/时间等保护；`unknown` 不得显示成硬限制。任一必需上限没有有限解析值时，Preflight 应要求补充或阻止执行；不允许空值代表无限。每个解析值需记录来源、强制级别、策略版本、使用的历史基线/价格版本及用户覆盖，并在启动前展示。

上述规则属于生成机制的规范，系数、绝对上限和具体配置条目仍由版本化策略维护，不在需求设计阶段编造为已批准的固定数值。不设置无限重试或无限费用。

### 6.2 异常恢复

错误记录之后按预先定义的恢复策略判断：有限退避重试、重做无副作用的 Preflight 等可以在批准范围内自动恢复；不确定是否已经提交、可能产生重复副作用或会改变实验条件的请求，不盲目重放。不可安全修复时停止相关步骤，保留事件和证据，明确提示人工介入。

### 6.3 Artifact

默认无自动到期，保留至人工删除。支持人工删除、导入和导出/备份。容量及低磁盘阈值根据实际磁盘配置成有限数值；空间不足时停止新增任务或大型 Artifact 写入、提示清理或扩容，禁止静默覆盖或自动删除旧证据。为状态、失败原因、删除标记和最小终态清单预留保底元数据空间；保底空间不足时明确记录清单未封存，不伪装完整。删除后保留审计标记，导入检查 schema/hash/引用闭包/解压容量/条目数/路径和覆盖冲突。密钥与敏感字段必须在持久化前过滤或脱敏；若无法可靠脱敏，不存储原始敏感正文。

## 7. OS 配置对实验有效性的约束

Windows、macOS、Linux 都属于首期目标平台。正式首期发布前，Windows、macOS、Linux 各至少有一个经验证的 OS/版本组合完成本机管理能力与受控真实 Agent/插件任务执行的核心闭环；每个后续正式声明支持的组合也必须具备独立证据。只有控制台可启动不算完整支持。处于开发或验证中的组合，若尚无经验证的强制隔离后端，可维护配置和查看既有结果，但不得执行需要强制隔离的真实任务，也不得标记为已验证支持。各 OS 的兼容规则、版本范围与隔离后端注册表属于可维护配置，而不是需求阶段固定的工具名单。统一安全契约、后端能力和兼容状态的权威定义见 `02_总体架构与领域设计.md` 第 7 节。本实验方案只补充一条规则：如果本次选择的 OS/版本/隔离 Profile 尚未达到所需支持状态，或必需安全能力无法证明，运行前检查必须将正式执行阻止或明确降级；不得以别的 OS 的通过证据替代当前组合证据。

## 8. 可复现测试环境与非功能故障场景

测试平台以独立 Git 仓库管理源码、需求/设计文档、功能目录映射、用例与故障场景、环境配方、依赖锁文件和验证脚本；万象术作为独立被测仓库/包固定到目标 commit 或包哈希，测试平台不能直接修改被测源码。每次环境实例/实验保存测试平台 commit 与 dirty 状态、万象术版本/commit/hash、Host/Node/包管理器/依赖锁摘要、OS/架构、工作区模板、输入数据/随机种子、网络与隔离 Profile、配置 hash 和清理结果。密钥只保存 Secret Reference，不进入 Git 或可导出普通文本。

EnvironmentProfile 支持一键创建、预检、启动、重置、停止、销毁和按同一 Profile 重建。环境实例与 EnvironmentManifest 关联运行记录；已销毁环境可根据配方重建，但对无法固定的远程 Provider、在线模型或外部数据要明示复现边界。环境状态至少区分 provisioning、ready、running、cleaned/destroyed、failed/dirty/cleanup_failed。环境可重建并不等于满足 OS 强制隔离，两个条件分别验收。

非功能故障场景必须按环节覆盖：环境建立/重置、Host/插件加载、功能配置校验/路由模拟、Agent/子 Agent、Provider 网络调用、工具执行、事件/Artifact 采集、Oracle/Rubric、持久化/崩溃、取消/进程树清理。网络负例至少包括 DNS 失败、连接超时、提交后断连、429、5xx、慢响应、usage 缺失。每个场景定义可控注入方式、随机种子、期望错误类别、是否安全重试、预算处理、Run/Case/Attempt 终态、证据、清理和副作用对账。优先使用 Stub/受控代理或隔离环境，不对无授权的真实服务制造破坏性网络故障。

## 9. 配置数据与设计决策的边界

不要求在需求/设计评审时永久锁定以下清单：所有首轮 Case 与预期、全部 Provider/模型名单、预算/配额的具体数值、每一种 OS 的完整版本枚举或最终隔离后端名称。这些均是平台配置功能应当支持管理的数据，日后可新增、修订、停用和版本化。

| 内容                                            | 所属层次                                               | 在本项目中的处理方式                                                                                                                                   |
| ----------------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------ |

## 10. 基线策略与可配置参数

- **实验策略：** 同题、配对、仅把万象术加载状态作为默认变化因素；同一 Case 的 OFF/ON 结果应使用共同 `pair_key`。
- **重复策略：** 首次探索可以只运行一轮，但只支持描述该次观测；需要讨论稳定趋势时，建议每个 Case/条件至少 3 次独立重复。重复数可配置，必须在运行前冻结。
- **预算策略：** 初次设置生成宽松但有限的默认档，并将每项实际限制显示给用户。建议值由本机资源、Provider 限额/价格和用途生成或由用户配置；若费用数据不可用，应显式配置硬上限或说明无法作费用判断，不能将空值解释为无限。
- **Artifact 策略：** 默认不自动过期，手工删除/导入/导出；配额结合可用磁盘和系统保留空间设置为有限数值。首次配置向导可以推荐宽松数值，但应允许调整并显示实际数值。
- **OS 策略：** Windows、macOS、Linux 都属于目标范围；支持版本、范围和隔离后端由兼容/后端注册表持续维护，不在核心规范写死。以已声明范围内的向后兼容为目标；新版本仍需按能力和证据更新状态，不因“兼容目标”自动视为验证通过。
