# AITestTools 需求与设计基线

**文档版本：** V2.17  
**阶段：** 需求与设计  
**产品：** AITestTools 通用 Agent 自动化评测平台  
**首个被测对象：** 万象术（vibe-fs）OpenCode 插件

**快速阅读入口：** 若希望先用业务语言理解项目目标、完整流程、56 个 package 与实际控制点的区别、界面和实验方式，请先阅读 [README_项目负责人阅读版.md](README_项目负责人阅读版.md)。该阅读版用于导读；具体需求、对象/状态、指标公式和验收规则以本文件及下列专业文档为准。

## 1. 产品目标

AITestTools 用于把真实工作任务转化为可维护、可复现、可自动执行的测试资产，并完成运行证据采集、结果判定、配置比较和回归复用。产品核心不是单次“跑任务并生成报告”，而是形成长期可演进的测试用例管理与评测闭环。

平台需要支持：

- 管理测试用例、不可变版本、测试集发布与审核，并按任务类型和难度组织覆盖；
- 导入并维护万象术功能/消融目录，检查依赖、互斥和配置有效性，生成无副作用的模拟路由；
- 一键创建、校验、重置、销毁和复现独立测试环境，完整记录环境版本与状态；
- 选择 Host、Agent/角色、插件功能配置、Provider/模型等级和运行策略；
- 可视化展示实际 Agent 调用链、节点状态、模型路由、工作事件与日志；
- 自动执行任务，记录实际行为和证据，判定任务结果；
- 按预先声明的协议比较插件整体 ON/OFF、受支持命名 Profile，以及具备真实控制手段的功能级干预，并比较不同模型等级下的差异；无独立控制入口的功能通过默认行为场景观察，不假设逐项开关；
- 对网络、Host、Agent、持久化、证据、评分和清理等阶段开展可复现的故障注入与恢复验证。

## 2. 首轮核心实验

首轮实验比较同一组任务在使用万象术（ON）和不使用万象术（OFF）时的表现，围绕三类指标分别报告结果：

- **快：** 单题耗时、执行批次耗时、从启动到结果封存的端到端耗时；
- **好：** 预先声明的任务预期是否满足、通过/失败/无法判定情况及可解释的质量评分；
- **省：** 输入/输出/总 Token、调用量及可核验或明确标注为估算的费用。

不预设 ON 必然更优，不把三类指标合并成没有事先定义权重的总分。平台是否执行完成、业务任务是否通过、两组结果是否具备可比性，是三个不同判断。

## 3. 核心使用闭环

1. 创建、导入或整理用例，明确任务目标、输入、前提、预期、判定方法、证据和清理要求。
2. 审核用例并发布不可变的 `DatasetRelease`，同时选择版本化路线、路由和运行策略。
3. 选择被测对象和候选条件，完成运行前检查并冻结本次实验协议。
4. 在符合目标平台安全边界的环境中执行任务，记录计划值、解析值与实际观测值。
5. 评测任务结果，查看时间、质量、Token/费用、缺失数据和协议偏离。
6. 将有价值的新任务或异常沉淀为候选用例，经确认、验证和审核后发布到后续回归集。

在正式运行之前，用户应先选择目标版本实际支持的运行配置入口或已有消融 Profile，再执行配置校验与路由模拟。功能目录是被测系统的节点/模块清单，不是开关面板；不能仅凭一个节点出现在 `nodes.json` 或 `profiles.json` 就推断它能被外部单独控制。只有已核实的外部设置、受支持的命名 Profile 或明确支持的测试接口，才能作为实验干预。配置有效不等于实际行为已经发生，执行后仍要用 Host/插件/Agent 的真实事件、日志和结果证据核对。测试环境通过版本化 EnvironmentProfile 一键建立，运行记录关联具体 EnvironmentManifest 与 Git/依赖快照。

## 4. 关键设计原则与取舍

### 4.1 以用例资产为中心，而非以一次运行脚本为中心

测试资产需要经过设计、审核、版本化和复用。实验中发现的问题只有在预期行为与判定方法得到确认后，才能进入正式回归集。用例的审核/发布状态与自动化准备度分开管理，因为“内容已审核”不代表“已具备自动执行条件”，而“存在脚本”也不代表预期合同正确。

### 4.2 分离计划、事实和结论

计划记录预定输入与条件；运行事实记录实际发生的行为；报告只根据事实和预先定义的规则计算结果。这样可以避免把配置选择误认为真实生效，也能在重跑、恢复和配置升级后保留可复核的依据。

### 4.3 用不可变版本和运行快照保证可复现

`Case` 表示稳定用例身份，`CaseRevision` 表示不可变内容版本，`DatasetRelease` 引用确切版本；正式运行冻结本次使用的配置与策略版本。目录和配置可以继续演进，但不能改写既有运行的输入、预算、路由、判定器或证据引用。

### 4.4 把计划条件与实际调用路径分开

首轮对照固定同一测试集、评测规则、路由策略和其他约定条件，只将插件加载状态作为默认实验因素。万象术本身引发的子 Agent/角色调用变化是需要观察的实际行为，不能仅因调用路径发生变化就判定实验不可比；未声明的配置漂移则必须单独披露。

### 4.5 通过配置注册表扩展，而不是硬编码所有清单

用例、Provider/Deployment/Model、路由、预算/配额、平台兼容规则和隔离后端均是可维护、可版本化的数据。需求与设计阶段需要定义其结构、校验、解析优先级、能力探测、兼容迁移和快照规则，不要求提前穷举全部用例、模型、OS 版本或后端。配置项只有在相应实现与证据满足要求后，才能标记为可用或已支持。

### 4.6 安全能力必须可强制执行

真实 Agent/插件任务必须满足目标操作系统上的文件、命令、网络、资源、凭据和进程清理等强制边界。普通工作目录或应用层路径检查不能替代操作系统级隔离。缺少必需安全能力时应阻止真实执行或进入明确受限模式，而不是降低安全要求来换取“能运行”。

### 4.7 预算宽松但有限，证据保留但不无限占用

预算与 Artifact 策略需可配置，运行前展示有限的实际值和来源。Artifact 默认不自动到期，支持人工删除、导入和导出，但有单文件、单次运行、全局容量和低磁盘保护；超限时应停止新增写入并提示，不能静默覆盖或自动删掉旧证据。

### 4.8 首期采用单机模块化方案

首期以本机安装和模块化单体为主，使 UI、CLI、应用服务和 Runner 共用一套状态、指标与执行契约。这样能先保证核心闭环可验证，再按明确的 Provider、平台和执行后端接口扩展，不需要在首期引入分布式调度和多租户系统的额外复杂度。

### 4.9 56 个 package 是目录节点，不是 56 个外部开关

固定参考版本的 `resources/ablation/nodes.json` 包含 56 个 `kind=package` 节点和 3 个 `kind=slice` 节点。这里的 package 是万象术消融拓扑中的模块/规范包节点；它首先回答“系统把哪些能力域纳入该拓扑”，并不直接回答“用户可以通过哪个参数把它单独打开或关闭”。功能节点可能由代码逻辑、资源、角色规则和其他节点共同实现；大部分默认行为可以按代码与资源中的既定规则运行，并不一定存在独立的外部配置项。

因此，界面必须分开呈现三种东西：

1. **功能/规范包目录：** 该版本有哪些 package/slice 节点、定义和关系。这是可浏览的清单，不默认可编辑。
2. **实际配置控制点：** 被测版本明确支持从外部调整的环境变量、配置字段、路由配置或其他接口，以及现有的命名 Profile 选择入口。固定版本 README 公开列出 `WANXIANGSHU_ABLATION_PROFILE` 用于选择消融拓扑 Profile；这说明可以选择 Profile，不等于界面可以任意改写其中每个节点。
3. **默认行为与可观测行为：** 没有受支持外部控制项的节点，按目标版本的默认行为运行；测试工具通过用例输入触发相关行为，并从实际结果/事件中观察。不能因为该节点在目录里有状态字段，就假设它有独立运行时开关。

每个节点应有“控制能力分类”：`documented_external_setting`（有公开外部控制点）、`named_profile_only`（只能选择已定义的 Profile/组合）、`verified_test_interface`（存在明确受支持的测试控制接口）、`fixed_default`（按版本内置默认行为执行）、`observational_only`（只能在任务中观察）或 `unknown`（证据不足）。控制方式、默认值来源、允许值、适用版本、运行时生效证据和可归因范围必须分别记录。不得把目录节点数、Profile 中的节点状态数和可独立控制项数混为一谈。

该版本 `profiles.json` 记录各个命名 Profile 对应的 `active / borrowed / ablated` 节点状态；状态映射是 Profile 的内容，不自动等于每个节点都可以在生产运行时单独覆盖。默认优先使用被测版本公开支持的既有 Profile 选择能力。若需要自定义单节点状态，必须先证明所选运行入口支持该自定义 Profile；若实现方式需要直接修改安装包内 `profiles.json`、资源或代码，应作为单独的源辅助/变体实验记录新的文件 hash、commit 和构建信息，不能冒充未修改的黑盒基线。

**示例：** 假设功能目录中有一个与子 Agent 委派有关的 package。测试平台可以展示它的定义、关系和默认行为来源，并设计需要多 Agent 协作的任务来观察实际调用。但如果万象术只公开了“选择某个命名 Profile”的入口，没有公开这个 package 的独立控制点，测试平台就只能比较已有 Profile 的整体差异，或记录该场景中的实际行为；不能凭目录名称生成“委派 ON/OFF”开关，更不能把结果差异单独归因于这个 package。若未来某个版本增加了受支持的独立配置入口，再在该版本对应的控制点清单和能力证据中启用单项实验。

`station` 是源元数据，存在重复值和缺号，不能作为唯一 ID 或唯一顺序。导入器必须保留源边类型并按各自语义校验：`station-order` 同时参与拓扑顺序，并在目标节点设为 `active` 时要求来源节点至少为 `borrowed`；`borrow` 在目标节点为 `borrowed` 或 `active` 时要求来源节点至少为 `borrowed`。两者有不同触发条件，但都不能直接改称通用业务硬依赖。硬依赖、源边状态约束、排序、互斥和交互关系分别建模；只有具有源配置或实现证据的关系才能用于阻断/归因。规范包节点与 `requirements/` 目录是不同的清单，需要针对同一被测 commit 做映射对账；差异要明示，不得补造开关或静默忽略。

### 4.10 黑盒结果判定与配置辅助控制

项目以黑盒端到端结果评测为主：质量由任务是否完成、外部可检查的产物、预先定义的 Oracle/Rubric 和人工评分决定；时间、Token、费用由运行事实与可追溯的计量来源决定。读取消融目录/关系图的用途是说明配置元数据、选择被测版本提供的控制入口和解释候选关系，不用节点名称代替任务结果，也不以内部文件内容直接判定任务质量。

整体插件 ON/OFF 和通过公开配置/Profile 选择的对照，可以作为受控实验。只有当某个功能有经过验证的单独控制手段、该手段真实生效，并且其他条件按协议固定时，才可以把实验称为该功能的单项消融并估计其独立差异。对无独立控制入口的功能，只能开展默认行为/场景覆盖、现有命名 Profile 的整体比较，或经明确标记的源辅助变体比较；不得从相关任务表现直接推断“这个 package 单独贡献了多少”。

### 4.11 模拟路由与实际路由分离

模拟路由仅可基于目标版本真实接受的配置形态或明确标记为假设方案的候选状态生成。对于当前运行入口不支持的任意节点覆盖，界面可以显示“假设性模拟/不可直接执行”，但不能显示为已验证、可一键运行的候选。实际运行路由必须来自 Host/插件/Agent 的事件和调用证据。两者分开存储、并排比较，是为了避免把“配置上计划如此”误认为“运行时确实如此”。

## 5. 首期范围与边界

首期必须形成真实纵向闭环：用例管理与发布、ON/OFF 对照、真实 Host/插件状态证据、受控执行、证据采集、结果评价、配对比较、预算/Artifact 管理，以及异常沉淀为候选回归用例。

Windows、macOS、Linux 均为首期目标平台，采用本机安装。**正式首期发布前，Windows、macOS、Linux 各至少要有一个经验证的 OS/版本组合能够完成核心任务执行闭环；此后每个新增的正式支持组合，也必须有该组合自身的兼容性与隔离证据。仅控制台可启动不等于完整的平台支持。** 尚未验证的组合可以进入配置与评估流程，但不能标记为已验证支持或执行需要强制隔离的真实任务。

首期可以人工维护模型目录和能力记录，采用可解释的 Oracle、Rubric 与人工复核，提供描述性比较统计；模型可按能力/质量档、成本档等可配置分层，并在每个模型层内完成同模型 ON/OFF 配对。首期不要求覆盖所有 Provider 协议、自动生成测试代码、分布式/集群执行、多租户权限平台、公开 Benchmark Registry、完整的 2^N 全因子搜索、复杂因果推断或自动化模型裁判校准平台。功能级实验框架应支持已有命名 Profile 对照；只有存在经验证的运行时单项控制点时，才开放单项消融；顺序累积和交互实验也只针对真实支持并可验证生效的控制项，不以穷举所有组合为首期前提。无外部开关的功能通过默认行为场景覆盖，不虚构单项干预。

## 8. 规范维护原则

同一概念只在一个权威位置定义，其他文档通过链接或引用说明使用方式。调整对象状态、指标公式、配置优先级或验收条件时，应同步检查需求追踪矩阵和相关模板；图示必须与规范对象及关系保持一致。文档描述的是应实现的行为与判断规则，不应把设计要求写成已运行验证通过的事实。
