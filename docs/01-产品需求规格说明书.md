# AITestTools 产品需求规格说明书（V2.17）

**状态：** 需求基线草案，供需求/设计评审  
**开发对象：** AITestTools  
**首个被测对象：** 万象术（vibe-fs）OpenCode 插件

## 1. 产品目标与问题定义

AITestTools 是通用 Agent 自动化评测平台。它让使用者能把需要验证的任务维护成版本化测试用例，选择 Agent、插件、模型和运行配置，自动执行测试、收集证据、按明确标准判定，并对不同配置做可靠比较。

产品核心价值包括：

1. **管理测试用例：** 用例有来源、预期、判定规则、版本和审核状态，可以持续补充、修订、发布和退役。
2. **自动执行与留证：** 运行过程可追踪，输入、配置、模型调用、产物、评分依据和结果之间可以相互关联。
3. **可信比较：** 使用同一批任务和预先声明的条件比较不同配置，不把环境差异、缺失 Token 或未执行任务伪装成性能提升。
4. **日常使用门槛低：** 普通用户通过可视化流程即可创建测试、检查设置、启动运行、查看失败和证据；CLI/API 提供自动化入口。
5. **可持续扩展：** 首期以万象术和 OpenCode 为主，但领域模型不把通用平台限制为单一插件、单个 Agent 或单一 Provider。

首轮业务问题为：**同一组任务在使用万象术和不使用万象术时，时间、任务质量、Token 消耗及费用有何差异？** 本项目不预设哪一方更好。

## 2. 用户与产品边界

| 用户              | 主要目标                       | 核心能力                                              |
| ----------------- | ------------------------------ | ----------------------------------------------------- |
| 测试设计者        | 把真实任务和问题变成可复用测试 | 创建/导入 Case，定义预期和 Oracle，组织 Dataset/Route |
| 测试执行者        | 选择配置并安全运行任务         | 选择用例集、检查配置和权限、运行、取消、查看进度      |
| 评测分析者        | 判断方案差异是否可信           | 对照任务结果、时间、质量、Token、费用和可比性限制     |
| 审核者/产品负责人 | 确认预期行为和正式用例         | 审核合同、Oracle 和异常候选，发布用例版本             |

**边界规则：** AITestTools 是本项目要开发的产品；万象术是被测对象。两个仓库保持独立。本项目不修改万象术源码，不把被测插件的专属业务逻辑复制到通用核心。Host（OpenCode）、Agent/角色、插件、模型/Provider 是不同配置维度，不得都笼统称为“模型配置”。

## 3. 典型用户流程

1. 创建或导入任务用例；补充任务目标、输入材料、前提、预期、判定方式和风险标签。
2. 将已确认用例组织成不可变 `DatasetRelease`；同时冻结各自版本的 `SuitePlan`、`ModelRoutingProfile` 和其他 Profile；对比时引用同一 DatasetRelease。
3. 选择被测对象、Host/Agent、Provider/模型路由、环境、权限、超时、预算和重复策略。
4. 运行前检查版本、配置、插件开关、数据引用、凭据可用性、权限、安全隔离、预算和指标可观测性。
5. 确认执行计划并运行；能看到每项任务真实状态、实际调用信息、失败/阻塞原因及证据采集状况。
6. 对任务结果执行机器判定、Rubric 评分或人工复核；不可判断时明确显示，不强行二分。
7. 查看任务级结果与“快、好、省”指标，先判断两组条件是否可比，再解读差值。
8. 对运行中发现的异常创建候选用例；经脱敏、分类、复现/Oracle 验证、审核后发布到新版本回归集。

## 4. 功能需求

### FR-01 用例和测试集管理

平台必须能创建、编辑、导入、检索、分类、审核、发布、弃用和复用测试用例。每个逻辑 `Case` 具有稳定 ID；每个正式 `CaseRevision` 至少包含：

- `case_id`、不可变 `case_revision_id`/修订号、任务目标、指令/输入材料及其来源；
- 可配置的 `task_type`、`difficulty_level`（建议统一使用经定义的有序等级）、难度判定理由、必需能力和风险标签；正式比较数据集要能按任务类型 × 难度检查覆盖；
- 适用 Host/Agent/插件/模型或环境前提；
- 任务预期、必须满足的要求与禁止副作用；
- Oracle 或 Rubric、评分维度、版本和适用范围；
- 用途/能力/行为类型/风险等标签、超时和资源要求；
- 来源 Run/异常（如适用）、审核状态、审核记录及内容哈希。

每个 `CaseRevision` 的生命周期采用 `draft → candidate → reviewed → validated → released → deprecated`；`Case` 只是稳定逻辑身份。状态名称可以映射到具体 UI，但发布条件必须清楚：未经确认的预期、未验证的 Oracle 或未经审核的异常不能直接成为正式回归用例。

另设独立的**自动化准备度**字段，至少区分 `not_assessed / manual_only / spec_incomplete / design_ready / blocked`。它与 Case 是否已审核/发布不是同一个状态：一个用例可以已被正式记录但仍需人工执行，也可以已具备完整的自动化规格但尚未实现执行器。用例设计记录应支持前置条件、步骤/动作、输入数据、预期合同、Oracle/Rubric、所需证据、初始化/清理操作、权限/副作用、可重复性和环境依赖；界面要指出缺少的字段和自动化障碍，帮助测试人员把巡检/异常整理成可执行规格。首期重点是结构化设计、质量检查和维护，不把“自动生成测试代码”作为未确认的必交能力。

### FR-02 持续用例建设与历史异常治理

用例库不要求在项目启动前一次性做完。实验过程中发现的新任务或异常，可以从对应 Run、Case、Event、Artifact 建立候选；随后进行脱敏、分类、指纹去重、复现/最小化、确认预期合同、设计判定器、自测试与独立审核。审核通过后，发布为新的 CaseRevision 和新的 DatasetRelease。

一次任务失败不自动说明是产品缺陷；它也可能是预期拒绝、环境/Provider 故障、数据问题、随机波动或未知原因。无法稳定复现或没有确定预期的异常可保留为 Observation，不得冒充确定性回归用例。

### FR-03 数据集与路线版本

正式 Run 必须引用已发布的不可变 `DatasetRelease`，并冻结所选 `SuitePlan`、`ModelRoutingProfile` 等各自版本的配置引用。修改 CaseRevision 的输入/预期、材料或 Oracle 后创建新 CaseRevision 和适用的新 DatasetRelease，保留差异与来源；不得原地修改历史 Run 引用的版本。自动运行计划只能纳入在运行前声明为本次范围、并满足该执行模式要求的用例；`manual_only`、`spec_incomplete` 或 `blocked` 的用例不能静默执行，也不能等到看到结果后再从分母移除。若用例未纳入自动运行范围，应在计划冻结时说明原因。现有 Item/Paperset/Room 资产在 V2.17 重构中迁移为 Case/CaseRevision/DatasetRelease 领域对象（见 02 §3.2），迁移保证历史 run 产物语义等价。

支持至少这些用途标签：冒烟/环境可用性、产品验收、诊断、回归、效果比较、受控故障和评分器校准。不同用途的结果不应在未声明的情况下混算。巡检原文是只读来源和路线参考，不自动等于正式需求或 Case。

### FR-04 计划、配置与运行

平台必须支持插件整体 ON/OFF 和已有受支持配置/Profile 的对照；当且仅当某项功能具备经验证的独立控制点时，才支持该项的单项启用/消融。对于可控项，还应支持符合依赖约束的累积实验和选定的交互实验。没有外部控制点的节点仍进入功能目录和用例覆盖映射，但只能做默认行为/场景观察，或标记为源辅助变体实验，不得伪装成单项开关。每个设计须标明干预方式、固定条件、模型层、任务类型/难度分层、归因范围和预算。不得默认穷举全部组合；实验矩阵预览要显示候选数量、预估运行量、可控项覆盖、仅观察项和未覆盖交互。

平台必须显式区分“计划定义、实验实例、运行批次和单项执行”四个层次：ExperimentPlan 是运行前冻结的协议；Experiment 是该协议的一次真实执行实例；Run 是其中一个候选/条件在一个预先声明执行块中的批次；CaseExecution 是 Run 内一个确切 CaseRevision 的一次计划观测。一次计划重跑应产生新的 Experiment ID，不得覆盖旧结果。

一次 Experiment Plan 至少记录：被测对象/Host/Agent/插件版本、实际可选的命名 Feature Profile 或经证明可被运行时接受的自定义配置、各外部控制点、模型路由 Profile、数据集版本、模型等级与具体模型/Deployment、实验变量、固定条件、环境 Profile/实例、权限、预算/超时/重试/并发、缓存/预热和状态重置策略、顺序策略、评分器、指标、故障注入 Profile、排除规则与清理策略。每个候选配置要区分目录节点状态、运行时可控能力、默认行为、实际干预方式、预计路由和可支持的归因级别。

运行前应展示候选数、Case 数、独立重复数、预估调用/Token/费用（无法估算时显示未知）、非法组合和阻断原因。用户确认后冻结计划，运行时不得默默修改变量或以新默认值覆盖原计划。

平台必须能区分：运行批次的生命周期、每个 Case 的执行结果、每个 Case 的评测结果、物理执行尝试与归因标签。重试不增加独立实验样本；独立重复必须使用不同的重复编号和执行记录。

### FR-05 多 Provider、模型资源池和 Agent 匹配

模型目录必须允许为模型定义可维护的分层标签，例如高能力/高质量、均衡、低成本等；分层名称、判据和成员可配置，不能把示例分层当成永久固定分类。每个层内开展万象术 ON/OFF 对照时，必须固定同一具体 Provider、Deployment、模型标识、参数配置和允许的 fallback 策略；跨模型层比较分别展示插件效果差异和模型本身差异，不能把模型变化引起的质量/成本差异直接归因给万象术。

平台允许多个 Provider 和 Deployment 并存，并将 Provider 连接器、Deployment、Model Catalog、能力记录和 Agent 路由作为可维护配置，而不是硬编码一份固定供应商/模型清单。用户应能在已支持的连接器范围内新增、导入、编辑、停用和验证 Provider/Deployment 与模型条目；Model Catalog 记录模型类别/能力、上下文与工具协议限制、结构化输出能力、usage 可观测性、价格来源和版本。凭据只保存 Secret Reference，不把密钥存入普通配置或导出文件。配置了某个名称不表示连接器或模型已经受支持：未知 Provider 协议需要对应 Adapter，能力未知时必须显示未验证，并在真实调用验证后更新证据。

Agent 的不同角色可映射到不同模型；同一模型也可分配给多个 Agent/角色。系统根据必需能力、可选能力、上下文、工具/结构化输出和预算约束给出兼容、有限兼容、不兼容或未验证及原因。匹配结果只是候选建议，不替代真实连接/调用验证。正式运行需记录计划路由策略和可观测到的实际路由；无法观测时明确标记未知。计划路由策略及允许的 fallback 规则是实验固定条件，但万象术启用后可能自然引起子 Agent、角色调用或模型调用次数变化，这类被测系统实际行为是观测结果，不应仅因实际调用路径不同就自动判为不可比较；只有发生未声明的配置漂移、超出允许策略的 fallback，或需要做模型身份归因却无法观测模型身份时，才按比较目标降级或阻断相应结论。

### FR-06 任务判定与质量评价

平台支持确定性 Oracle、规则评分、模型辅助评分和人工评审，并清楚区分评分来源。正式 Case 的 Oracle 应定义输入证据、预期合同、通过/失败/无法判定的含义、版本和理由；至少要覆盖正例、反例、边界和证据缺失情形的自测试。

不能客观规则化的质量维度可用 Rubric 评分，例如要求满足度、正确性、完整性、工具使用合理性和产物质量。ON/OFF 两组必须使用相同版本的 Oracle/Rubric；适用时对评分者隐藏候选标签，降低评价偏差。未经独立样本校准的模型裁判必须标为实验性/未校准，不能充当已校准的硬门禁。

### FR-07 指标和可比性

首轮核心指标为“快、好、省”，定义见 `04_首期实验方案与用例治理.md`。平台必须分别显示指标口径、单位、分子/分母、来源、缺失处理、聚合范围和版本；不得把未知 Token/费用当成 0，不得用没有预先声明权重的总分选冠军。

正式比较前检查测试集版本、候选差异、Provider/模型身份、预算、权限、计时/采集方式、评分器、执行顺序和缺失数据等条件。条件不满足时可以保留诊断数据，但不得生成无条件的正式提升结论。比较结果应能下钻到配对 Case 和原始证据。

### FR-08 证据和可追溯性

每次正式运行需能追溯到不可变的计划快照、运行过程中追加的事实/事件/产物，以及终态汇总。证据至少覆盖：版本、Case/Release、配置快照、Host/插件加载或未加载事实、模型调用/usage（在 Provider 能提供时）、执行时间、退出码、工具/事件轨迹、工作区差异、Oracle 结果、清理状态与 Artifact 哈希。

原始证据不得静默覆盖，但这不意味着允许将密钥或无关敏感信息明文持久化。敏感字段应在写入持久化存储前按规则排除或脱敏；若无法可靠脱敏，则不保存该敏感正文，只保存采集受限事件、必要元数据及可用时的完整性摘要。任何脱敏产物应指向来源 ID、脱敏规则版本和脱敏后哈希；在威胁模型允许的情况下保留可访问的源证据引用，但不能为了“保留原始证据”而泄露凭据。没有观测到的事实标为 `unknown/not_observed/unsupported`，不得从用户选择的配置值推断它必然生效。

### FR-09 跨平台本机运行

首期目标平台是 Windows、macOS 和 Linux，本机安装与执行是首期方式。正式首期发布前，Windows、macOS、Linux 各至少有一个经验证的 OS/版本组合能够完成核心产品闭环（包括受控的真实 Agent/插件任务执行、证据采集与结果查看）；此后每个正式声明支持的 OS/版本组合也必须满足该要求。仅能启动 Console 不算完整支持。开发/验证阶段尚未完成隔离验证的组合可进入评估流程，但不得标记为已验证支持，也不得执行需要强制隔离的真实任务。平台支持范围不能写死在源码常量中，应由可维护的 `PlatformCompatibilityRule` 与支持矩阵表达 OS 版本、CPU 架构、Node/npm/OpenCode/万象术版本约束，以及 Host/依赖/隔离后端的适用范围。规则支持精确版本与版本范围、能力要求、例外、弃用状态和证据引用；具体版本清单是配置数据，可持续追加/修订，不要求在需求设计阶段穷举所有版本。

兼容策略以维持已声明支持范围内的向后兼容为目标：已验证的旧组合保留独立证据，只有在明确弃用策略后才退出支持；新 OS/Host/运行时版本可通过版本规则与能力探测进入评估，但不得仅因落入宽泛版本范围就自动标为 `verified_supported`。支持状态及其唯一语义见 `02_总体架构与领域设计.md` 第 7.3 节。未知版本或能力不足时，解释缺口并阻止依赖该能力的正式/安全运行，或明确降级为受限模式。依赖升级时创建新配置/矩阵修订，并根据变更影响重跑相关 OS/版本组合的安装、加载、核心任务、采集、取消清理和安全回归；不能覆盖旧证据，也不能将一个 OS 的证据继承到另一个 OS。

### FR-10 运行预算、故障处理和有限恢复

每次运行必须引用可配置的 `BudgetPolicy` 与解析后的 `BudgetProfile`。策略的生成规则、参数和版本本身也应可配置/可维护；可以根据可用 CPU/内存、磁盘余量、Provider 限额与价格、usage 可观测能力和实验用途生成宽松建议值，并允许用户覆盖。Profile 至少包含任务/批次时限、Provider 调用数、输入/输出/总 Token、费用、重试次数、并发和系统资源上限。每次正式运行必须解析为有限、可观察、可修改的实际值，记录取值来源/策略版本并在执行前展示。没有可靠数据时必须要求补充设置或显式披露未知，不能空值代表无限，也不能承诺无法强制执行的费用上限。

Provider 或环境异常需记录阶段、稳定错误类别、请求/关联 ID（可得时）、消耗与已尝试动作。仅对事先定义、有限、可逆且满足幂等条件的情形自动恢复。不得自动改换未经批准的 Provider/模型、扩大权限、变更实验变量或掩盖异常；无法安全修复时提示人员介入，并说明发生了什么、已经尝试了什么、接下来需要人做什么。

### FR-11 Artifact 生命周期与空间管理

Artifact 默认不自动过期，保留到用户/管理员人工删除。用户可以按权限查看、导入、导出/备份和删除；导入需验证版本、大小、路径安全和哈希，避免覆盖已有历史对象。删除前显示影响范围；删除后保留最小审计/删除标记，不能悄悄让历史证据看起来仍可访问。

单文件、单次 Run、全局存储和低磁盘保护值由可版本化 `ArtifactPolicy` 管理；首次配置可以根据实际存储容量、现有占用、保留系统空间和运行用途生成建议值，具体生成策略与参数可以调整。每次 Run 展示解析后的有限数值及来源。宽松保留策略不代表容量无限，也不得静默覆盖或自动清理旧证据。达到上限时停止新增写入或相关任务，并明确提示清理/扩容。

### FR-12 操作系统级安全边界

真实 Agent/插件任务应在目标 OS 提供的有效隔离机制下执行。平台通过可维护的 `IsolationBackend` 注册表和 `IsolationProfile` 配置，为 OS/版本/架构/运行权限匹配合适后端及参数；后端名称、适用范围、实现版本、支持能力、证据与限制都需可追踪。设计定义共同安全契约，包括文件读写边界、允许命令、网络出口、进程权限、CPU/内存/时长上限、凭据注入范围、超时/取消和进程树清理；具体后端与参数可以随着支持版本迭代，不要求产品需求阶段锁定某一种实现。配置无法创建一个尚未实现的系统能力：后端必须已注册并具备对应实现，能力探测与验证结果满足要求后才可使用。仅使用独立目录、设置 HOME/XDG 或依赖应用层路径检查，不得称为操作系统级安全隔离。

若某个平台/版本无法强制实现某项必需边界，其对应 Profile 应标为受限或阻止真实执行，说明具体缺口；不能把未隔离的真实执行包装成安全执行，也不能通过修改普通配置关闭强制安全条件。

### FR-13 万象术功能目录、依赖图与模拟路由

平台必须提供专用可视化页面，显示目标万象术版本已识别的 package/slice 节点、定义、源文件、关系、默认行为说明、实际配置入口、控制范围和可观测证据。参考固定 commit 的 `nodes.json` 包含 56 个 `kind=package` 节点和 3 个 `kind=slice` 节点；该数字是消融拓扑的目录计数，不是 56 个独立外部开关。实际目录从同一被测 commit 的 `nodes.json`、`profiles.json`、`fact-map.json`、`tool-map.json`、`requirements/` 清单和相关实现导入并校验，分别统计 package/slice 节点、公开外部配置点、可选择的源 Profile、可验证单独干预项、固定默认/仅观察项和未知控制项。节点与 `requirements/` 目录不能假定天然一一对应；映射差异必须呈现，不得伪造开关。

每个节点至少表达稳定 ID、目标版本、显示名、节点类型、源文件/hash、默认行为/值来源、源关系、借用前置条件、经证实的硬依赖、互斥/交互关系、源 Profile 状态、真实外部控制点引用、控制范围、单独覆盖是否受支持、控制证据、可观测证据及归因限制。`active / borrowed / ablated` 是消融 Profile 中的状态语义，不自动等同于 UI 可以分别设置的运行时开关。若需要自定义节点状态，必须证明目标运行入口能接受该配置；直接改写安装包资源或源代码的情形要单独标注为源辅助变体，并冻结新 hash/commit。

该版本必须分别保留 `station-order` 与 `borrow`：两者均参与图与状态校验，但触发条件不同。`station-order` 参与顺序计算，且当 `to=active` 时要求 `from` 为 `active` 或 `borrowed`；`borrow` 在 `to=borrowed` 或 `to=active` 时要求 `from` 为 `active` 或 `borrowed`。两类边都不能被改称为通用业务硬依赖；未知边类型应保留并阻断受影响 Profile 的发布。校验还须检查源版本/引用、合法状态、已证实依赖、互斥和环。

只有对于目标运行时实际支持的既有 Profile 或经验证的干预配置，系统才可生成标记为“可执行候选”的模拟路由。对无法由实际控制入口表达的状态组合，只能生成明确标记为“假设性”的模拟，不得提供一键运行或单项效果归因。所有模拟都不得调用模型、启动真实 Agent 或写目标工作区；运行后再以 Host/Agent/Provider 事件与调用证据核对实际路径。

### FR-14 Agent 工作链路可视化与日志

运行详情必须实时或准实时显示 Agent/角色调用链和工作流状态。可视化以实际 `AgentInvocation`/Event 为事实来源，展示父子调用关系、节点状态、开始/结束时间、等待/重试/失败、实际 Provider/Deployment/模型（能观测时）、工具调用、Token/费用、日志与 Artifact 引用。状态至少能区分 queued、running、waiting、completed、failed、cancelled、blocked、interrupted、unknown；UI 不得将没有事件的节点伪装为正在运行，也不得以计划路由代替真实轨迹。每条日志/事件应可按 Experiment、Run、CaseExecution、AgentInvocation、请求/关联 ID 下钻。

当 Host 或 Adapter 不提供实时状态/某些日志时，界面应显示最近观测时间、不可观测字段及原因；Agent 子任务丢失、父子状态不一致和取消未清理应产生明确异常状态。预先计算的模拟链路与实际执行链路必须采用不同标签/视觉标识。

### FR-15 独立 Git 项目与可复现测试环境

AITestTools 测试平台必须作为独立 Git 项目管理自己的源码、需求/设计文档、功能目录映射、用例/故障场景、环境定义、锁文件、验证脚本和报告生成规则；不得把平台文件混入万象术上游仓库，也不得为了测试直接修改被测插件。每次实验需记录测试平台 Git commit、工作树是否干净、万象术固定 commit/包哈希、Host/运行时版本、锁文件/依赖摘要及所有环境配置版本；凭据与个人机密只保留 Secret Reference，不能提交到 Git。

平台必须支持按版本化 `EnvironmentProfile` 一键创建/准备、预检、启动、重置、停止、清理、弃用/销毁与重新建立测试环境。环境定义至少包括 OS/架构、Host/插件版本、运行时/包管理器和锁文件、Provider/模型路由引用、测试数据与随机种子、工作区模板、外部状态重置方式、网络策略、预算、隔离 Profile、环境变量白名单与 Secret Reference。每个实际实例产生 `EnvironmentManifest`，记录实际解析版本、安装/启动结果、资源状态、文件/配置 hash、环境 ID、来源 Git commit、创建/重置/销毁事件与清理结果。重新建立同一 Profile 时应能验证重要版本和输入一致，并报告无法完全复现的外部依赖。

环境准备和可复现性与操作系统安全隔离是两个不同能力：环境可创建并不代表环境具备强制安全边界。真实 Agent/插件任务仍须满足 FR-12 的 OS 隔离要求。环境清理失败时实例标为 dirty/cleanup_failed，不得假装已销毁；一键操作必须有预检、进度、取消/失败说明和可审计日志。

### FR-16 分阶段非功能故障场景与恢复验证

平台必须管理可版本化的故障场景/注入 Profile，并能在受控测试环境或可替换的模拟 Provider/Host 中复现网络和各执行阶段异常。覆盖至少包括：DNS 失败、连接/读取超时、请求提交后断连、限流（429）、临时服务错误（5xx）、慢响应/响应中断、Provider usage 缺失、Host/插件加载失败、Agent 子调用失败、功能依赖错误/模拟路由失败、环境创建/重置/销毁失败、磁盘不足/Artifact 写入或 hash 失败、Oracle 超时/缺证据、持久化失败/进程崩溃、取消与进程树清理失败。

每个场景必须声明注入阶段、触发条件/种子、预期错误分类、是否可安全重试、预算/状态影响、期望 Run/Case/Attempt 终态、证据与清理要求以及是否产生副作用。至少覆盖 Runner/Adapter 的 resolve、preflight、prepare、submit/start、query/status、collect、evaluate、cleanup 全阶段。对“请求已提交但响应丢失”这类状态未知情形，应先查询/对账或转人工处理，禁止无幂等依据重复执行；错误恢复不得偷偷切换模型、扩大权限或改变实验变量。真实外部网络/生产系统不得作为不可控故障注入目标，优先使用 stub、代理故障规则和隔离环境。

## 5. 首期产品范围

### 5.1 首期必须交付的产品能力

首期必须形成一个可被普通测试人员使用、也可被自动化流程调用的真实纵向闭环：

- 可创建/导入、编辑、审核、版本化和发布测试用例与不可变 DatasetRelease；支持将运行中的异常转成候选并经过审核进入后续回归集。
- 提供本机可视化控制台和稳定的 CLI 自动化入口；两者调用同一应用服务/状态契约，不各自实现另一套业务逻辑。内部 HTTP API 可用于本机界面，不因此自动承诺为外部稳定公共 API。
- 对首个被测对象 OpenCode + 万象术，能够区分计划 ON/OFF 与真实加载证据；同题比较时按已冻结协议运行、采集证据并呈现快/好/省指标。
- 配置目录能够同时保存多个 Provider/Deployment/Model 条目，并能选择已注册且实际实现的 Provider Adapter；首期不要求对所有厂商协议自动发现，但不能把任意名称录入误称为已接通。
- 具备模型池到 Agent/角色的基础能力匹配与版本化路由；模型按可配置等级分组，在同等级内完成相同模型 ON/OFF 配对；能力字段可以手动维护并带来源/验证状态，未验证能力不得冒充兼容。
- 提供万象术功能/消融目录、依赖与交互关系的可视化配置、校验和无副作用模拟路由；功能级实验能够生成单项、依赖顺序累积和选定交互矩阵。
- 提供 Agent 工作链路图、节点实时/准实时状态、实际调用路由和关联日志/证据下钻。
- 提供独立 Git 项目管理与版本化的一键环境创建、重置、销毁、复现和环境清单。
- 具有可维护的非功能故障场景矩阵，能在受控环境验证网络和关键执行阶段的异常处理、状态完整性和安全恢复。
- 提供预算与 Artifact 策略配置、实际值解析、用户确认、运行快照、超限行为和人工导入/导出/删除。
- Windows、macOS、Linux 均为首期目标平台；每个实际声明为首期支持的 OS/版本组合都必须有独立证据。执行 Agent/插件任务前必须满足该组合的强制隔离契约，否则真实执行被阻止，不允许用其他 OS 的证据代替。
- 对每个纳入运行计划的任务记录清晰的终态或阻断/未运行原因；运行事实、评分和比较结论可下钻到证据。

### 5.2 首期可先采用的简化方式

首期可以使用人工维护的 Provider/Model Catalog，不强制自动发现所有模型；可以先采用单机模块化架构和项目现有的数据持久化能力；质量评价以可解释的 Oracle、Rubric 和人工复核为主；比较结果优先提供可复算的描述统计，不强制实现高级显著性检验或自动化因果推断。

### 5.3 明确不属于首期必交能力

首期不要求一次支持所有 Provider 协议、自动生成测试代码、公开 Benchmark Registry、分布式/集群执行、多用户/多租户权限平台、任意仪表盘、自动化模型裁判校准平台或复杂的全因子实验优化。架构可留接口，但不能用“可扩展”掩盖首期核心闭环不完整。

### 5.4 非功能性设计基线

- **可复现：** 每次正式运行都能追溯到不可变计划快照、DatasetRelease、配置修订、规则/价格版本、执行事实和 Artifact 哈希；任何未观测项明确为未知。
- **一致性：** UI、CLI、API/导出使用同一应用服务的状态和指标结果；同一版本的公式、分母、单位及缺失值处理一致。
- **故障恢复：** 进程异常退出后，系统识别未封存 Run，保留已写入事实并进入对账/恢复状态；绝不自动将其补记为完成或无依据地重放有副作用的请求。
- **数据完整性：** Release 和 Run 快照逻辑不可变；Artifact 内容哈希可验证；导入有路径、大小、引用和版本检查；损坏/缺失显示为不可读取而不伪装为正常。
- **安全与隐私：** 采用最小权限和可执行隔离边界；密钥不写入普通配置/导出或未脱敏日志；能力不满足时 fail closed。对于本机文件所有者可直接修改文件的威胁边界，系统提供篡改检测能力但不夸称抵御本机管理员。
- **可维护和兼容：** 配置对象、运行清单、事件、评分和指标有 schema/version 与迁移/拒绝策略；新增平台版本以可配置兼容规则评估，不覆盖旧验证证据。
- **性能与容量：** 时间、并发和容量等数值由 Profile/策略配置；产品需求阶段不编造固定 SLA，但运行前必须解析实际限制并展示，超限行为确定且不静默丢证据。
- **交互可理解：** 所有阻断/警告给出原因、影响对象和可执行的下一步；未知不能显示为 0，计划值不能显示成观测事实。

## 6. 需求验收标准

产品需求被视为定义完整，至少须满足：

1. 每个正式 `CaseRevision` 有明确输入、前提、预期、判定方式和来源；`Case` 逻辑身份、修订状态与自动化准备度分明。
2. DatasetRelease 可冻结并逐项引用确切 CaseRevision；SuitePlan/ModelRoutingProfile 等配置独立版本化，历史 Run 能引用原版本。
3. 正常、预期失败、边界/缺证据和受控故障能被表达；所有纳入计划的 Case 最终有明确终态或明确阻塞/未运行原因。
4. 同题 ON/OFF 的固定因素、唯一实验变量、评分规则、计时边界、Token 来源和排除规则能在运行前查看。
5. 报告可以分别解释时间、质量、Token/费用；缺失值、分母和可比性限制显式显示，不自动综合排名。
6. Provider/模型匹配显示依据与未知项；计划配置不冒充真实运行时调用。
7. Windows/macOS/Linux 均列为目标；具体支持声明以 OS/版本组合证据为准。
8. 预算与 Artifact 策略可以调整并解析为有限实际值；异常恢复和安全边界有明确的禁止行为。
9. 普通用户能够通过 UI 完成选择测试集、预检、运行、查看状态和证据的基本流程；具体页面与展示规则见 `03_界面与交互设计.md`。
10. 每项需求能在 `需求追踪矩阵.csv` 中找到可验证的验收描述和权威设计章节。
11. Case/预期、Provider/模型、路由、预算/配额、平台兼容规则和隔离 Profile 均由可维护配置/注册表管理；修改后有版本与来源记录，并且不改写历史 Run 快照。
12. 支持范围能够通过版本范围、能力探测、独立证据和弃用策略持续演进；新增版本不需改写核心规范中的硬编码清单，未知组合不会自动被视为已验证支持。
13. Experiment/Run/CaseExecution 的层级与 pair_key 定义明确；同题 ON/OFF 的对应样本和独立重复可唯一配对，技术重试不增加统计样本。
14. 时间指标的起止边界、批次与 Case 范围明确；质量指标按预声明量表和适用样本计算；每项指标显示有效样本数、缺失原因和聚合口径。
15. 计划路由固定与实际调用路由分开记录；由被测插件引起的预期路径变化作为结果保留，未声明配置漂移则按目标结论降级/阻断。
16. 功能目录从固定万象术版本导入，分别记录源 package/slice 节点、真实公开的外部控制点、可选命名 Profile 和经验证的独立干预项；默认行为/仅观察节点不得显示为虚构开关。若固定版本基线仍是 56 个 package 节点和 3 个 slice 节点，应在同一 commit/hash 下验证并显示，不把该数字写死为未来版本常量。对同一 commit 的节点、Profile、`requirements/` 清单和实现做映射对账；保留 `station-order`、`borrow` 源边并按各自语义验证。模拟路由区分可执行候选与假设性模拟。
17. 支持整体插件 ON/OFF 和目标版本真实支持的 Profile 对照。单项消融、依赖累积和交互实验只针对存在经验证控制手段的因素；无控制手段的节点进入场景覆盖/观察映射，不作单项因果归因。矩阵需显示配置变化范围、有效独立变量、覆盖缺口与预计运行量，不默认穷举 2^N 组合。
18. 数据集可按 task_type 与 difficulty_level 分层检查覆盖；模型等级可配置；同等级下每一 ON/OFF 配对使用同一确切模型/Deployment/参数，跨等级结论不会误归因给插件。
19. 运行界面能显示真实 Agent 调用链、节点状态和关联日志；不可观测状态明确显示 unknown/stale，不用模拟轨迹替代实际事件。
20. 一键环境生命周期支持创建/验证/重置/停止/销毁/重建，EnvironmentManifest 记录 Git commit、依赖/版本、配置 hash、数据种子、外部状态重置、网络/隔离配置和清理结果；不能复现的外部依赖明确披露。
21. 非功能故障矩阵覆盖网络、Provider/Host、功能路由、环境、Artifact、评分、持久化、崩溃、取消/清理等场景；未知副作用不得盲目重试，所有注入结果有对应状态、日志和证据。
22. 启动前冻结计划；进程崩溃、导入损坏或 Artifact 不完整时，历史记录能显示中断/缺失状态，不伪造成完整成功；敏感信息不会因证据留存而明文泄露。

## 7. 需求外事项

本需求说明书不包含源码修复任务明细、实现排期、工程人员分工、实际运行通过记录或问题关闭情况。这些属于后续阶段的独立工程管理工作，不应与产品需求混为一谈。
